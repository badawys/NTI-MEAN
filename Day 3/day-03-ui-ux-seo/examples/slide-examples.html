Block 1

User research & information architecture

Design begins by understanding the people, goals, pain points, decisions, and routes—not by choosing colors.

Slide 7 · terms

Client, user, and persona

Client
The person or organization paying for the solution.
User
The person who actually uses the application.
Persona
A simple realistic profile representing one important user type.
Goal
What the user wants to achieve.
Pain point
What currently makes the workflow difficult.

Slide 10 · comparison

Journey vs flow

User journey

The full experience before, during, and after app use—including feelings, doubts, and decisions.

User flow

The exact screen-by-screen path, actions, branches, and transitions inside the app.

Block 2

Responsive wireframes & visual hierarchy

A wireframe shows content, order, actions, states, and responsive behavior before visual polish.

Slide 17

Wireframe purpose

  • Shows structure and layout priority
  • Avoids detailed decoration
  • Supports early client review
  • Plans components and forms
Slide 18

Visual hierarchy

  • Make the primary action easy to find
  • Use headings for location and structure
  • Group related content with spacing
  • Use size and contrast for priority
Slide 19

Consistency

  • Keep button meanings stable
  • Make validation predictable
  • Reuse course and table patterns
  • Keep navigation stable
Slide 20

Responsive basics

  • Start with content
  • Use one column on small screens
  • Use filters/tables/side panels when space allows
  • Keep touch targets easy to tap

Slides 24–25 · content-first output

Write before decorating

  • Use real headings
  • Name buttons by action
  • Write empty and error states
  • Plan reusable card, button, table, field, and alert components

Responsive notes must describe what stacks, scrolls, moves, hides, or remains fixed—without changing the reading order.

Block 3

Accessibility & usability

Semantics, labels, keyboard behavior, contrast, and useful states are part of the experience—not optional cleanup.

Slide 28 · semantic HTML

Meaning before styling

<main>
  <h1>Angular Foundations</h1>
  <section aria-labelledby="facts">
    <h2 id="facts">Course facts</h2>
    <a href="/login">Sign in to register</a>
  </section>
</main>

Slide 31 · contrast

Readability rules

Readable text uses sufficient contrast, comfortable line height, and a useful line length.

Error: email format is invalid

The error includes text and structure, not only red color.

Slides 32–34 · usability output

Five beginner checks

  1. Understand the goal in five seconds?
  2. Complete the task without explanation?
  3. Primary and secondary actions distinct?
  4. Useful empty state?
  5. Useful failure state?

The final accessibility notes must cover landmarks/headings, form rules, keyboard order, contrast, empty/loading/error/success states, image alt text, known limitations, and the improvement plan.
